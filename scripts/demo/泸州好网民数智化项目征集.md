## 支撑“Agent”称谓的部分

按经典 AI 定义（Russell & Norvig：感知环境→自主决策→执行行动），整个系统构成了完整的 agent 闭环：

| Agent 要素 | 你项目中的对应 |
|---|---|
| 感知（sensors） | 7 路采集：音频转写、剪贴板、文件监听、飞书事件、网页抓取 |
| 行动（actuators） | 写入 inbox、触发编译、建索引、更新图谱、托盘开关 |
| 常驻自治 | 后台常驻、无感采集、新素材到达自动触发编译（FR-011） |
| 持久记忆 | knowledge/ 知识库 + LightRAG 向量与图谱，就是长期记忆 |
| 自主行为 | 限流暂停、重试、增量幂等、质量闭环自查自纠 |

这套“持续维护一个开放目标（知识库）而非响应单次请求”的形态，比一问一答的 chatbot 更接近 agent 的本质。

## 按 2024-2025 严格 LLM-Agent 定义看不足

业内（如 Anthropic《Building Effective Agents》）区分 **workflow**（代码编排固定流程，LLM 在节点里干活）和 **agent**（LLM 自己掌握控制流，动态决定下一步用什么工具）：

- **编译层**：九步流水线是**代码写死的顺序**，LLM 只在各步骤当“打工人”，不决定流程走向 → 是 workflow
- **问答层**：LightRAG 的检索模式（naive/hybrid/mix）是**配置参数**，不是 LLM 运行时自主选择工具 → 是 RAG，不是 agentic tool-use
- 缺少运行时的规划-反思循环（LLM 自主拆解任务→执行→评估→调整）

## 实际建议

- **申报/产品语境**：放心叫 Agent。市面上大量同类产品（固定流水线 + LLM 节点 + 自动触发）都这么命名，评审不会苛责。
- **论文/答辩语境**：表述更严谨些，如“自主知识管理系统”“基于 LLM 的多源知识采集与图谱问答 Agent（系统级自治 + 流水线式 LLM 编译）”，主动说清架构，反而显得理解深。
- **若想名副其实地“更 Agent"**，演进方向：① 编译层让 LLM 动态调度（自己决定处理顺序和策略）；② 问答层加 tool-use（LLM 自选检索模式、图谱查询、返回溯源）；③ 加反思环节（编译后自评质量决定是否重跑）。

**Assistant**

`(.venv)` 表示你当前终端里**激活了一个名为 `.venv` 的 Python 虚拟环境**。

**虚拟环境是什么**：一套独立、隔离的 Python 运行环境，有自己的解释器和第三方包目录。作用是让每个项目的依赖互不干扰、不污染系统全局 Python。

**对你的实际影响**：

- 此刻运行的 `python`、`pip` 都是 `.venv` 里的，不是系统全局的
- `pip install xxx` 只会装进这个环境（本项目 [requirements.txt](file:///d:/learning_code/09-knowseq-agent/requirements.txt) 里的 fastapi、lightrag-hku 等就装在这里）
- 运行本项目（`python run.py`）就需要在这个激活状态下执行，否则会找不到依赖

**常用操作**（PowerShell）：

```powershell
deactivate                                # 退出虚拟环境，前缀消失
.\.venv\Scripts\Activate.ps1              # 重新激活
.\.venv\Scripts\python.exe run.py         # 不激活也可直接用完整路径调用
```

提示：如果激活时报“禁止运行脚本”，先执行 `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` 一次即可。
